# ParserGeneratorCC internals

Notes on how the generator works, derived from the code rather than from the upstream JavaCC
documentation. They exist because the algorithm classes carry almost no prose: `NfaState` is 3,598
lines with four upstream `TODO(sreeni): fix this mess` markers and no explanation of what it builds.

- [The pipeline](pipeline.md) — what happens between reading a grammar and writing the files
- [Generator state](state.md) — where the state of a run lives and why
- [The template language](template-language.md) — `#if`, `${...}` and how a template becomes a file
- [Bootstrapping](bootstrapping.md) — the project is generated by a released version of itself

## Where to start reading

| If you want to change… | Start at |
|---|---|
| what the parser code looks like | `ParseGenJava` / `ParseGenCPP` |
| what the token manager looks like | `LexGenJava` / `LexGenCpp` and `templates/{java,cpp}/TokenManager*.template` |

## The rule that governs all of it

The generated output is the product. `GeneratedOutputGoldenTest` pins 386 generated files across 38
option and grammar combinations to a SHA-256 manifest, so any change to the code generation fails
the build until somebody looks at it. Re-bless deliberately:

```
mvn test -Dtest=GeneratedOutputGoldenTest -Dpgcc.golden.update=true
git diff src/test/resources/golden
```

Reading that diff is the point. Re-blessing without reading it defeats the harness.
